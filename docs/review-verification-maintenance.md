# 怎样持续校准 review 与 verification

负责相应产品区域的维护者拥有验收承诺；负责 CI 的维护者拥有执行器和结果解析。遇到漏检、误报、规则变更和设备用例抖动时按下表处理。每月维护者从近期 PR 和 Early 回归中抽样复盘；这是维护约定，无定时 AI 作业。

| 事件 | 收集什么 | 如何改 |
|---|---|---|
| 合并后出现回归、回退或补修 | 引入提交和修复、受影响用户、触发步骤、哪一层最早可以观察到它 | 优先给业务入口加能在旧错版本失败的测试。能从 diff 判定且重复出现的问题再写进审查清单。 |
| 本地 Codex 报了错误的须修项或反复提出相同发现 | 当前 head、原意见、作者解释、是否实际修改、轮数 | 在独立上下文复跑同一 diff。调整判据或严重性，用干净对照防止过度拦截。 |
| 慢测试、间歇失败、CI 或设备缺失 | 第一次失败的步骤/日志、工具与 OS 版本、重跑差异 | 区分未完成、基线故障和产品回归。若暂时隔离，记负责人、替代证据和复查日期。 |
| 提议删测试、改变触发范围或放宽门禁 | 原用例覆盖的失败、替代测试、风险和运行时间 | 在旧缺陷和稳定版本分别重放；独立维护者确认仍能发现原失败。 |

## 一次规则变更的交付标准

1. 用一份小 PR 同时提交触发条件、用户承诺、适用平台、执行命令、期望证据、负责人和来源 PR。更新相关单测、脚本与文档链接。评审该规则时使用目标分支现行的标准。
2. 选择一个包含已知缺陷的历史版本和一份大小相近的稳定对照。隐藏修复、事先写一句正确答案。审核规则修改前、修改后分别跑两者；记录检出、误报与未完成。调参样本和保留验收样本分开。
3. 判断应落在哪层。快速可复现的业务不变量放 PR；昂贵的真实设备/模型场景按风险运行或放 Early。对相同旧数据执行两版做差分；比较持久化结果时只归一化明确无关的时间戳等字段。
4. 新的主观标准先旁路记录“本会阻断什么”。抽样没有触发的 PR，检查路由漏检。历史缺陷稳定检出、稳定对照的误报已解释、失败有人处理，再单独提议强制。业务负责人批准涉及用户行为、隐私或兼容性的例外。
5. 复盘时对照合并后补修/回退、每 PR 有效须修项、等待人工时间、复审轮数、CI 未完成率和场景耗时。分别定位 reviewer 没发现、发现后误判、最终报告漏报。流量小时报告原始数量与样本，删掉被更可靠检查覆盖的规则。

可从 [#492 离线记录删除/恢复](https://github.com/memex-lab/memex/pull/492) 和 [#483 WAL 备份](https://github.com/memex-lab/memex/pull/483) 开始建样本。复盘只保存合成数据和脱敏证据。相关方法见 [Anthropic verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/) 和 [Anthropic review](https://claude.dev/blog/solving-code-review-at-anthropic/)。
